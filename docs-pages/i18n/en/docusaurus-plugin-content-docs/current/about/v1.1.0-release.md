# python-office 1.1.0 Release: the `po` CLI

> **One line of code for office automation** — python-office 1.1.0 was released on October 26, 2026.

If you already use python-office, this release has one headline: **it now ships a command-line entry point called `po`.** Colleagues without a Python environment, people who prefer the terminal, and teams wiring up AI agents can all use it now.

If you have not used python-office yet, this post doubles as a complete introduction.

---

## What changed in this release

1.1.0 is a **feature-level minor release** with three main parts:

| Change | Content | Impact |
|---|---|---|
| 🆕 **New CLI** | `po` command, 7 modules, 42 subcommands | Use it without writing Python |
| 🆕 **5 new Skills** | Excel data-checking methods | Completes the "spreadsheet" toolchain |
| ⚡ **Performance** | `import office` now uses PEP 562 lazy loading | Smaller installs, faster startup |

The four key commits:

| Commit | Content |
|---|---|
| `f297919` | feat(cli): first wave of CLI implementation — the `po` command (#184) |
| `630e909` | feat(contributors): 5 new Excel data-checking methods (#185) |
| `fa00cba` | fix(skills): contributor Skill fallback raised NameError instead of ImportError |
| `2618b6a` | release: bump version to 1.1.0 |

After `pip install python-office`, the terminal entry point is ready:

```bash
po --version
# po 1.1.0 (python-office)
```

## The `po` command: 42 subcommands across 7 modules

```text
po
├── pdf       (11)  convert, merge, split, encrypt/decrypt, watermark
├── excel     (7)   fake data, merge/split, search, export to PDF
├── file      (8)   batch rename, search, group by name
├── image     (8)   compress, watermark, word cloud, QR code, pencil sketch
├── tools     (6)   translate, URL-to-IP, password, generate article
├── markdown  (1)   Excel to Markdown
└── finance   (1)   stock T+0 profit calculation
```

That's **7 modules, 42 subcommands, 121 parameters** in total.

### Three everyday use cases

**Merge PDFs**

```bash
po pdf merge2pdf report-a.pdf report-b.pdf --output-file merged.pdf
```

**Excel to PDF**

```bash
po excel excel2pdf report.xlsx report.pdf
```

**Resolve a domain to an IP**

```bash
po tools url2ip www.python-office.com
```

### Two-level command structure

Like most CLI tools, it follows `<module> <subcommand> [positional args] [--options]`. Every subcommand has its own `--help`:

```bash
po --help                  # list all 7 modules
po pdf --help              # list the 11 pdf subcommands
po pdf merge2pdf --help    # inspect one subcommand's parameters
```

### Parameter style: kebab-case long options

Python parameters use underscores (`input_file`); the CLI converts them to kebab-case (`--input-file`):

```bash
po file replace4filename ./dir "old text" --file-rename true --suffix .txt
```

Boolean parameters accept `true/false/1/0/yes/no/on/off`.

### Platform guard: a mechanism reserved for Windows-only features

Some python-office features depend on Office on Windows (Word→PDF, PPT handling). The dispatch layer is designed to **check the platform guard before importing** — a module that does not belong on the target platform is intercepted up front with a clear message, instead of making you dig through a stack trace.

All 7 modules registered in this wave are cross-platform, so no module currently triggers the guard. The mechanism itself is covered by tests: a Windows-only module is injected to verify interception behavior, producing a message like

```text
po: error: module 'xxx' is only available on: win32 (current: darwin)
```

Meanwhile, **modules not included in this wave (word / ppt / video / web / wechat, …) simply do not exist yet**:

```bash
po ppt ppt2pdf
# po: error: argument <module>: invalid choice: 'ppt' (choose from excel, file, finance, image, markdown, pdf, tools)
```

When the second wave adds those modules, the Windows-only parts will go through the guard — **guard first, import second, so cross-platform calls trigger no import at all.**

### Design: a declarative registry

The CLI core is a declarative registry (`office/cli/commands.py`) where each command declares its own parameters:

```python
"pdf2docx": {
    "help": "Convert PDF to docx",
    "params": [
        {"name": "input_file", "positional": True, "metavar": "PDF",
         "help": "input PDF file"},
        {"name": "output_file", "help": "output docx file"},
    ],
},
```

Two direct benefits:

- **`po --help` has zero dependencies.** Building the parser imports no `office.api` module, so even if you only installed `popdf`, `po --help` still opens instantly instead of failing on a missing heavy dependency.
- **Adding a command is just adding a data entry.** No changes to the dispatch or argument-parsing logic.

Dispatch also filters arguments with `inspect.signature`, so extra fields in the registry never reach the API function as a `TypeError`.

## Why `--json` matters more than the command itself

This is the most underrated part of 1.1.0, and arguably the most valuable.

```bash
po --json tools url2ip www.python-office.com
```

Output is **a single line of JSON**, with stdout clean enough to pipe straight into a script:

```json
{"ok": true, "result": "1.2.3.4"}
```

Errors are also one line, with exit code 1:

```json
{"ok": false, "error": "FileNotFoundError: [Errno 2] No such file or directory: 'a.pdf'"}
```

### A subtle detail

python-office's internals call `print` themselves (progress bars, for instance). Left alone, stdout would be polluted with progress output and script parsing would break.

`po` redirects **all library-internal output to stderr**, guaranteeing stdout contains only that one JSON line:

```text
stdout:  {"ok": true, "result": null}      ← only this line
stderr:  rows: 100%|██████████| 5/5 ...    ← progress bar lives here
```

Many people miss this boundary, but it is the dividing line between "a CLI you can call" and "a CLI a script can rely on."

### Why this matters for AI agents

AI agents (Claude Code, Cursor, Codex, …) need structured output when they run commands. Unstructured output means either parse failures or progress-bar noise mistaken for the result.

`po --json` is a natural fit for agent tool calling:

| Need | How `po --json` answers it |
|---|---|
| Did it succeed? | Check the `ok` field — no error-text parsing |
| What was the result? | Read `result` |
| Why did it fail? | Read `error` |
| Should I continue? | Check the exit code (0 success / 1 failure) |

So if you are building an agent workflow, **python-office's 81 Skills now have a unified command-line entry point.**

### Existing Python usage is untouched

The CLI is zero-intrusion by design. All previous styles keep working:

```python
import office
office.pdf.pdf2docx()          # unchanged
from office import pdf         # unchanged
from office import *           # unchanged
```

## Imports got faster: PEP 562 lazy loading

The most easily overlooked change in 1.1.0 — and the one with the biggest effect on day-to-day experience.

### Before

```python
import office
```

This dragged in the dependency tree of **all 14 API modules** — `poexcel`, `popdf`, `povideo`, `poocr`, `pospider` and everything they pull. Even if you only wanted PDF handling, you installed the whole set.

### After

Python ≥ 3.7 uses PEP 562 module-level `__getattr__` for on-demand loading:

```python
import office          # loads no po* sublibrary
office.pdf             # imports office.api.pdf → popdf only now
```

Measured behavior (Python 3.12):

```text
po* modules loaded after `import office`: []          ← empty
after accessing office.pdf: popdf, pofile, ...         ← loaded on demand
```

### Practical benefits

| Benefit | Explanation |
|---|---|
| **Install size** | PDF-only users no longer install povideo / poocr / pospider |
| **Startup time** | `import office` is no longer a long wait |
| **Docker images** | A core CLI image needs only 8 sublibraries; the full dependency set includes moviepy and paddleocr, which take minutes to install |
| **Compatibility** | Python 3.6 has no PEP 562 and falls back to the original eager import — behavior unchanged |

### A trade-off to watch

`office/__init__.py` no longer contains real `from office.api import ...` statements, so **IDE "go to definition" and autocomplete degrade**. If your editor no longer jumps to the definition of `office.pdf` or offers no completions, this is a known side effect of 1.1.0.

The maintainer accepted the contribution as-is but explicitly logged the cost: if the community reports worse navigation, the lazy loading could be pushed down into `office/cli/` while `office/__init__.py` stays as it was. **If you rely heavily on IDE navigation, verify it after upgrading.**

## 5 new Excel data-checking methods

Alongside the CLI, contributors filled a gap in the spreadsheet toolchain. Existing methods handled **format conversion and merging**; these add **diffing, deduping, and profiling**.

### Overview

| Method | What it does | Difference from existing methods |
|---|---|---|
| `excel_diff` | Compare two workbooks cell by cell | `merge2excel` merges; this finds differences |
| `excel_dedupe` | Dedupe by column or whole row | No existing duplicate detection |
| `excel_column_stats` | Per-column profile: fill rate, type, unique count, value distribution | `find_excel_data` searches by keyword; this profiles by column |
| `excel2json` | Sheet to JSON, three structures | `excel2markdown` is for humans; this is for programs |
| `excel2csv` | Export CSV, multi-sheet batch | `excel2pdf` outputs PDF; this outputs plain text |

All depend only on `openpyxl` (already in the dependency chain), are Python 3.6+ compatible, and **introduce no new third-party packages**.

### excel_diff: key-based pairing avoids "one inserted row marks everything red"

```python
from skills.excel import excel_diff

result = excel_diff(
    before_path='last-week.xlsx',
    after_path='this-week.xlsx',
    key_column='order_id',
    output_path='diff.xlsx',
)

print(result['summary'])
for item in result['changes']:
    print(item['key'], item['column'], item['before'], '->', item['after'])
```

Two comparison modes:

- **By position** (default): cell-by-cell, for tables with a stable row order.
- **By key** (via `key_column`): pair rows by key first, then compare fields within each key.

Why key mode matters: with row numbers alone, inserting one row in the middle marks **every subsequent row** as changed. Pairing on a unique identifier — order number, student ID, employee number — means row reordering produces no noise.

**Duplicate or empty keys raise an error** rather than silently returning a wrong comparison. That is a professional trade-off.

### excel_dedupe: returns duplicate details, not just a count

```python
from skills.excel import excel_dedupe

result = excel_dedupe(
    excel_path='customers.xlsx',
    key_columns='phone',
    keep='first',
)

print(result['total'], result['unique'], result['duplicate_count'])
for dup in result['duplicates']:
    print(dup['row'], 'duplicates', dup['kept_row'])
```

When debugging you need to know "row 5 duplicates row 2" — a bare `duplicate_count` number is not actionable.

### excel2csv: utf-8-sig by default fixes Chinese mojibake

```python
from skills.excel import excel2csv

result = excel2csv(
    excel_path='report.xlsx',
    output_dir='./csv',
)
```

**The default encoding is `utf-8-sig` (with BOM)** — the single most common pain point for Chinese users: saving as plain UTF-8 and double-clicking in Excel produces garbled characters, while BOM does not.

For Linux toolchains, pass `encoding='utf-8'` explicitly.

### excel2json: three structures, pick by downstream

```python
from skills.excel import excel2json

# records (default): [{"name": "Alice", "dept": "Sales"}, ...]
# columns: {"name": ["Alice", "Bob"], "dept": ["Sales", "Marketing"]}
# values: [["Alice", "Sales"], ["Bob", "Marketing"]]
result = excel2json(excel_path='report.xlsx', orient='records')
```

`excel2json` is for programs, `excel2markdown` is for people — complementary, not redundant.

### excel_column_stats: a health report for a spreadsheet

```python
from skills.excel import excel_column_stats

result = excel_column_stats(excel_path='report.xlsx', top_n=5)
```

Reports fill rate, inferred type, unique value count, numeric distribution and top values per column — you can immediately see which column holds the dirty data.

### Usage: import by Skill category

```python
from skills.excel import excel_diff, excel_dedupe, excel_column_stats, excel2json, excel2csv
```

> ⚠️ **Note**: the implementations of these 6 contributor Skills (`batch_rename_by_excel` plus the 5 above) live in the repository's `contributors/` directory, which is **not published in the pip package**. Installing from PyPI and calling them raises a clear ImportError telling you to clone the repo or copy the file. This is inherent to the isolated-contribution model, not a bug.

## How the two PRs came together

Everything in 1.1.0 came from community contributors. A few details of the collaboration are worth recording.

### PR #184: CLI design trade-offs

Edwin.JH.Lee submitted the first wave of CLI implementation, proposing **incremental waves**: this wave covers 7 core modules with 42 subcommands; the rest (video / web / word / ppt / wechat, 20 commands) follow later. The registry structure is already in place, so adding them is purely a data-entry task.

The contributor built their own test infrastructure — the most valuable part of the PR:

| Test layer | Count | Notes |
|---|---|---|
| `pytest tests/test_code/test_cli.py` | 37 passed | Built-in `po*` stubs, so **CI runs without heavy dependencies** |
| `.x-cmd/test.sh` real mode | 15/15 | Real transforms + artifact checks (txt2pdf→merge2pdf page count, excel2markdown table, url2ip real DNS) |
| `.x-cmd/test.sh` stub mode | 10/10 | Automatic fallback in dependency-free environments |

`.x-cmd/Dockerfile` provides a clean `python:3.10-slim` image with apt and pip pointed at the aliyun mirror. The contributor documented one deployment prerequisite: PyMuPDF needs `libgl1 libglib2.0-0`, a slim-image missing-library issue rather than a PR defect.

**The most notable review comment** concerns the PEP 562 lazy loading:

> The benefit here is real — `import office` no longer drags in heavy dependency trees like poexcel/popdf/povideo, which helps both CLI startup and install size. But there is a hidden cost: with no real `from office.api import ...` statements left in `__init__.py`, IDE "go to definition" and autocomplete degrade.

The maintainer's handling: **accept the contributor's approach, but record the cost**, with a stated fallback — lazy loading could later move inside `office/cli/` while the core module stays unchanged.

The review also named three things done well:

1. Five commits cleanly separated (registry / parsing-dispatch / output / lazy loading / docs), still readable after squashing
2. Preloading `po*` stubs so CI runs without heavy dependencies
3. A dedicated test case verifying "stdout stays clean even when the library prints by itself" — **a boundary many people miss**

### PR #185: trade-offs in the Excel toolchain

Contributor my12yyds added 5 Excel methods with 39 unit tests.

One **collaboration detail worth noting**: when #183 was merged, the maintainer found that the contributor had added `skills/file/batch_rename_by_excel/` but had not registered it in the parent `skills/file/__init__.py`. As a result `from skills.file import batch_rename_by_excel` raised ImportError, inconsistent with every sibling Skill. The maintainer added a separate `chore(skills)` commit (`dd6f543`) to complete the registration, noting "if you would rather submit this registration yourself, you can revert `dd6f543` and open a new one."

By #185, the contributor **proactively registered in the parent `skills/excel/__init__.py`**, appending strictly at the end without touching existing lines — precisely the step missed in #183. The maintainer called this out in the review.

Another detail: the wording of `DECLARATION.md`. The contributor proactively clarified that "core maintainer" refers only to the responsible maintainer of that contribution module, and does not imply any maintenance or release rights over the upstream project. The maintainer noted the phrasing "shows good sense of proportion."

### One bug caught three times in a row

All 6 Skills from #183 and #185 used a try/except fallback for the case where the `contributors/` directory is absent from the installed package. But the code had a flaw:

```python
except ImportError as _import_error:
    def xxx(*args, **kwargs):
        raise ImportError('...') from _import_error
```

Python 3 **automatically `del`s the name bound by `as` when the `except` block ends**, so the closure's `_import_error` is an undefined name. In a real pip-installed environment (where `contributors/` does not exist), calling these Skills actually raised:

```text
NameError: name '_import_error' is not defined
```

instead of the intended ImportError with clear guidance.

The fix stores the exception in a module-level variable:

```python
except ImportError as _import_error:
    _CONTRIBUTORS_IMPORT_ERROR = _import_error

    def xxx(*args, **kwargs):
        raise ImportError('...') from _CONTRIBUTORS_IMPORT_ERROR
```

Regression coverage was added in `tests/test_code/test_contributors_skill_fallback.py`, explicitly mocking the contributors import to trigger the fallback. **This branch never fires naturally inside the source repository**, so regular test runs could not catch it — reverting the fix makes all 12 new subtests fail.

### One project-level collaboration rule

The handling of #181 / #182 reveals the project's current convention: **contributions that modify `office/` or other core directories need a discussion issue first, not a direct PR.** Isolated contributions (a `contributors/` directory plus a `skills/` wrapper) can be submitted directly.

The value of this rule: **the core directory is not repeatedly disturbed by "drive-by fix" PRs**, while new contributors do not have to fear accidentally breaking main.

## How to upgrade

```bash
pip install python-office --upgrade
```

For users in mainland China, use a mirror:

```bash
pip install -i https://mirrors.aliyun.com/pypi/simple python-office --upgrade
```

Verify the install:

```bash
po --version
# po 1.1.0 (python-office)

po --help
# 7 modules, 42 subcommands
```

If you only want the CLI and not every dependency:

```bash
pip install python-office popdf poexcel poimage pofile wftools pomarkdown
```

### Quick reference: all usage modes

| Usage | Scenario | Example |
|---|---|---|
| `po` command | Work directly in the terminal | `po pdf merge2pdf a.pdf b.pdf` |
| `po --json` | Scripts / CI / AI agent calls | `po --json tools url2ip example.com` |
